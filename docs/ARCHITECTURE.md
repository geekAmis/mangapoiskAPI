# MangaPoisk Reborn — architecture

## Goals

MangaPoisk Reborn is a Russian-language manga catalogue, search and reading
platform.  It is designed as an API-first product:

- **web** (React SPA),
- **Android** (native Compose client),
- **public API** for third-party clients,
- **offline exports** (CBZ / PDF / HTML) for reading without internet.

The old Flask/FastAPI prototype was a single process with hard-coded cookies,
print-debugging and direct HTML scraping.  The new system keeps the useful
behaviour (Russian catalogue, reader, offline downloads) and removes the
fragile parts.

### Admin / server manager

`control` stores servers (SSH credentials encrypted with a key derived from
`CONTROL_SECRET_KEY`), the microservices assigned to each server, and
deployment jobs.  It can install the selected services over SSH or through a
jump host, write systemd units and health-check them.  `/api/v1/admin/*` is
protected by an admin JWT issued from `ADMIN_USERNAME`/`ADMIN_PASSWORD`.
The gateway periodically pulls `/internal/registry` and switches a service to
the first healthy endpoint (non-fallback first, then fallback).  This is how a
server can be replaced without redeploying the web client.  The 83 jump host is
just an SSH route; it is not used for application traffic.

## Key decisions

1. **API-first.** Every feature is available through `/api/v1`; the web and
   Android clients use the same contract.  OpenAPI is generated by FastAPI.
2. **Normalised source layer.** Adapters return `MangaSummary`, `MangaDetail`,
   `ChapterDetail` (see `packages/manga_common/manga_common/source_models.py`).
   No HTML selectors leak into catalog or clients.
3. **Catalogue is a cache, not a mirror.** `catalog` stores metadata and page
   URLs.  Images are streamed through `media` and cached on disk.  We never
   redistribute images as our own content.
4. **Polite scraping.** One shared token bucket per upstream, exponential
   backoff, `Retry-After` support, conservative defaults, no CAPTCHA/anti-bot
   bypass, no paywall/DRM circumvention.  Optional user cookies are opt-in via
   environment variables and never committed.
5. **Failure isolation.** A broken source returns `502` from `parser`; the rest
   of the catalogue keeps working from PostgreSQL.  Circuit-breaker style
   caching means one outage does not cascade.
6. **Offline by design.** `media` builds a stable archive from cached images;
   exports are background jobs with progress and TTL cleanup.

## Data flow

### Search

1. `gateway` queries `catalog` (local, fast, already imported).
2. If `live=true` or the local result is empty, `gateway` asks `parser` to
   search the selected source.
3. Results are normalised, imported into `catalog` (upsert by
   `source + source_id`) and returned.

### Reading

1. `gateway` resolves `chapter_id` in `catalog`.
2. If page URLs are missing/stale, `catalog` calls `parser` for the chapter and
   stores `pages` JSON.
3. The reader requests images from
   `gateway /api/v1/chapters/{id}/images/{n}`; `gateway` passes the trusted
   page URL to `media`, which downloads, caches and streams it.
4. Progress is written to `library` (debounced client-side).

### Refresh

`scheduler` calls `catalog /internal/maintenance/refresh` every
`SYNC_INTERVAL_SECONDS`.  Catalog refreshes the N stalest manga, imports new
chapters, and returns a summary.  Scheduler forwards new-chapter events to
`notifier` (Telegram), if configured.

### Persistent chapter archive

When a reader opens a chapter, `gateway` sends the resolved page URLs to
`media` in the background.  `media` downloads the images through the same
polite cache and rate limiter as normal image proxying, then stores the result
once for every future reader.  The archive row is keyed by chapter and records
the source and translator it was fetched with.

- Chapters up to `ARCHIVE_DB_THRESHOLD_BYTES` (default 1 MiB) are stored as
  page BLOBs in SQLite (`ARCHIVE_DB`, default `data/archives.db`).  This gives
  fast random page access without a file per image.
- Larger chapters are packed into `ARCHIVE_DIR/{chapter_id}.zip` with
  `{number:04d}.{ext}` entries plus `manifest.json` (source, translator, page
  count, dimensions).

Archive creation never blocks the reader.  `gateway
/api/v1/chapters/{id}/images/{n}` tries the archive first and only falls back
to the original source URL when the page is not archived yet.  On startup,
unfinished jobs are marked failed and temporary files are removed.  Readiness
reports the archive database and directory separately from the image cache.

## Security

- Internal routes require `X-Internal-Token`.
- Public auth uses short-lived JWT access tokens and rotated opaque refresh
  tokens stored as SHA-256 hashes.
- Passwords use Argon2id.
- The gateway never accepts arbitrary image URLs from clients; it only proxies
  URLs already stored in `catalog`.
- CORS is explicit; production must set `CORS_ORIGINS`.
- No secrets in git.  `.env` is ignored; `.env.example` is documentation only.

## Non-goals

- Circumventing access controls, DRM, paywalls or anti-bot challenges.
- Hosting a full copy of third-party image libraries.
- Scraping private user data.
